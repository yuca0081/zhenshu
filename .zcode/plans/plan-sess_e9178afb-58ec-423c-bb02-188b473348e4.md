## 目标

在"检查通过、渲染开始之前"插入一道**渲染前画面预审**：用 hyperframes snapshot 一次性给所有段截 3 帧 → 视觉模型按画面审查同款考卷判分 → 有问题的段当场回喂重画 → 全部过关才进渲染。渲染后的全量 frameQA 降级为薄保险（只复查预审动过的段）。同时在画面生成提示词里加动效手感指导，治"生硬"的源头。

## 改动清单

### 1. 新文件 `server/internal/produce/prereview.go`（核心，约 300 行）

- **`preReview(ctx, p) (repaired []string, err error)`**：主函数。只让 ctx 取消向上传播；基础设施失败（snapshot/视觉模型单段调用失败）按 frameQA 同款"宁放过不误杀"降级——manifest 记账后跳过，不挡制作。
  - 开头读开关：project.json `pre_review`（`*bool`，缺省=开，`false`=整段跳过 return nil，照 `sfxFor` 模式）。关闭时 run() 走现状全量 frameQA。
  - 时刻映射 `preReviewTimes`：复用 sceneReplayCheck 的累计法（每段时长=audio_meta 的 DurationS+SegTail），每段取 0.5s / 中点 / 尾-0.5s 三个全局时刻（避开段首尾 0.25s 黑场渐变），返回 `ats[]` + `t2seg` 表。sceneReplayCheck 只覆盖含 canvas 的段，预审覆盖**全部段**。
  - 截帧：`pipeline.RunCLI(p, "npx", "hyperframes@0.8.55", "snapshot", ".", "--at", <逗号时刻>, "--no-end", "--no-browser-gpu", "-o", "reports/prereview/round<N>")`，每轮前 RemoveAll 防残留；帧文件名用现成的 `reSnapAt` 正则反解时刻→查表归段。
  - PNG→JPG 缩水：用 `pipeline.FFmpegPath()` 按帧转 1280 宽 `-q:v 4`（与 frameQA extractFrames 同参），控制视觉 token 成本。
  - 审查：`preReviewPrompt` 构造考卷（system 与 frameQA 相同；图1=开场后0.5s/图2=中段/图3=落定前；rubric 复用 frameqa.go 现成的 specHasScene 特化块、styleCheckBlock、sigqa 的 criteriaBlock；verdict 直接复用 `frameVerdict`），`GenerateJSONVisionEffort(..., llm.EffortHigh)`，并发 3，判分口径同 frameQA：无 high 问题即过。
  - 修复轮回 ≤2 轮：失败段把 issues 拼成逐项修改要求 → `r.sceneGen(ctx, p, "", feedback, <失败段>)` → `clearFrames` → `pipeline.Run(compositions)` → `assemble.py` → 重新 snapshot+审查。每轮 manifest `prereview.repair`。
  - 2 轮仍不过：**不阻塞**——emit stage 标红 + manifest `prereview.failed`，照常进渲染（这些段已在 repaired 集合里，渲后薄保险会兜住）。
  - 事件：`stage=prereview` 的 running/done/error；manifest `prereview.start/pass/failed/seg/review_error`。

### 2. `produce.go` run() 接线（约 10 行）

- 在步骤 4（checkWithRepair）与步骤 5（渲染）之间插 **4.5 预审**：`repaired := r.preReview(ctx, p)`。
- 步骤 6 改为薄保险：预审开启且 repaired 为空 → 跳过 frameQA（manifest `frameqa.skipped_by_prereview`，stitch 已在步骤 5 完成无缺口）；否则 `r.frameQA(ctx, p, "", strings.Join(repaired, ","))` 只复查动过的段（frameQA 的 only 语义现成）。`pre_review:false` 时行为与现状完全一致。

### 3. `scenegen.go` 画面生成提示词加"动效手感"节（约 8 行）

在布局规则后追加硬要求：入场禁 ease:"none" 平移淡入裸套路；主元素预备-落定（轻回弹 back.out 类，人文/庄重风格改绵长缓入缓出，与已注入的风格气质一致）；次要元素跟随主元素滞后 0.1–0.3s；错峰间隔随旁白短语节拍变化、禁全元素同秒砸入；出场干脆不拖尾。

### 4. 测试 `prereview_test.go`

- 纯函数表测：`preReviewTimes`（多段/钳位/缺 composition 跳过）、issues→feedback 构造、开关解析（照 methods_test 范式，t.TempDir）。
- 手动实测：`PRE_REVIEW_TEST=1` 环境门控走真 snapshot+视觉模型（照 frameqa_manual_test 范式，默认 skip）。
- 全量 `go build ./... && go vet ./... && go test ./...` 保持绿。

## 关键设计决策（已按现状定死）

- **发现即修，位置在渲染前**：返工成本从"渲完整片后重渲该段"提前为"渲染还没开始"。
- **非阻塞哲学与 frameQA 一致**：预审失败不杀制作，标红放行，渲后薄保险兜底；预审基础设施故障静默降级为现状行为。
- **已知取舍**：snapshot 时刻最早 0.5s，frameQA 的 t=0 首帧穿帮硬闸覆盖略弱（0.5s 帧仍能抓"晚出元素提前出现"）；预审修复轮不重跑 hyperframes check（与 frameQA 修复轮同口径），layout 回归由渲后薄保险兜住。两条都记录在代码注释里。
- **rework 路径不动**：段级重做本来就只渲 1-2 段，加预审不划算；跨段学习（前段踩坑喂后段）留作后续。

2. 提醒：Go 改动需重启 server 进程才生效（Windows 旧进程镜像坑）。
