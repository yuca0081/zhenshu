## 一、【P0·后端】para05 契约检查引号敏感（报告第四节）

### 根因
两处字面量匹配，双双只认双引号：

- `server/internal/produce/scenegen.go:623`
  ```go
  if !strings.Contains(html, `window.__timelines["`+segID+`"]`) {
  ```
- `ai/scene_lint.py:98`
  ```python
  if seg and f'window.__timelines["{seg}"]' not in html:
  ```

para05 的 13 次生成（transcript `llm/transcripts/seg.write.para05.jsonl`）每次都写了
`window.__timelines['para05']=tl;`——JS 语义完全等价，但检查不认。模型收到「未注册」
的回喂后无从修正（它确实注册了），于是 3+3 轮恒定失败 → 自动重跑 2/2 烧完 →
produce.error。其余 8 个单元恰好用了双引号，纯随机逃过。

附带发现：`scenegen.go:620` 的 `data-composition-id="segID"` 与 `scene_lint.py` F2 的
正则同样是双引号专属，存在同型脆弱性（HTML 单引号属性合法）。仓库里正确写法已有先例：
`pipeline/samplecheck.go:391` 的 `["']main["']`。

### 修复
1. **scenegen.go**（与 lint 同步改，缺一不可——两个门都挡着）：
   - `:620` 与 `:623` 改为引号无关正则：
     ```go
     var timelineReg = regexp.MustCompile(`window\.__timelines\s*\[\s*["']%s["']\s*\]`) // %s=regexp.QuoteMeta(segID)
     ```
     `data-composition-id` 同理：`data-composition-id\s*=\s*["']id["']`。
   - 报错文案保留双引号范本不变（它是对人的说明，不是对匹配器的）。
2. **ai/scene_lint.py:98（F3）与 F2 的 id 正则**：同款放宽：
   `re.search(r'window\.__timelines\s*\[\s*["\']' + re.escape(seg) + r'["\']\s*\]', html)`。
3. **提示词双保险**（可选，低成本）：`paraprompt.go:74`、`scenegen.go:790` 的契约第 3 条
   追加一句「单双引号均可，key 必须是段落 id 逐字一致」。

不采用「落盘前机械改写单引号→双引号」的方案：检查器放宽即闭环，不改写模型产物。

### 验证
- 单测：`scenegen` 契约检查用例加单引号变体（ timelines 单引号 / 属性单引号 / 混合空格）必须通过；双引号金样例不回归。`scene_lint` 同步加 Python 侧用例。
- 真项目续跑：修后对 `p20261030-102845` 对话栏发「继续」——para05 现存产出无需重写即可过检（transcript 里任一版本都含注册行），预期该单元一次通过。

### 附带建议（报告第四节「无降级/跳段」）
`fallbackOldScene`（scenegen.go:580）只救「有旧产物的重做」；首写恒定失败目前只能整轮
produce.error 后靠用户口头跳段。可在 `segpipe` 段链失败汇总里把「同错误连续 N 轮」标记为
`恒定失败` 并在 NotifyResult 的话术里显式给出跳段指令模板（后端已有全部信息，前端零改动）。
属增强项，不阻塞本批。

## 二、【P0·前端】请求无超时 + inflight 饿死（根因 B，P1-1/2/3/4 共同机制）

### 根因
- `web/src/api.ts:9-13` `authFetch` 直接 `fetch(input, init)`，**没有任何超时**。后端被外部
  重启/代理悬空时，请求可以挂几分钟（浏览器/代理层超时兜底）。
- `web/src/App.vue:121` 的 `inflight` 去重：`if (inflight.get(key) === seq) return`——同 key
  请求**在途期间所有后续触发全部静默跳过**，直到 `finally` 执行。一次挂住的
  `loadProject/loadMsgs/loadActivity` = 对应数据面冻结整段挂住期（不切项目不解锁，seq 不变）。
- 叠加测试环境实况（后端 5 次外部重启 + Vite dev server 因并行改文件自重启），半开请求
  反复出现：聊天 5 分钟不动（P1-4）、取消后视频页永远转圈（P1-3）、过程页冻在 10:41:03
  （P2-5 一部分）都是它在不同数据面上的投影。

### 修复（`web/src/api.ts`）
1. `authFetch` 统一注入超时：
   ```ts
   const DEFAULT_TIMEOUT = 30_000
   async function authFetch(input, init, timeoutMs = DEFAULT_TIMEOUT) {
     const signal = AbortSignal.timeout(timeoutMs)   // 与调用方自带 signal 组合：AbortSignal.any
     ...
   }
   ```
   例外放行：`regenCover`（同步截图，给 180s）；SSE 不走 authFetch。
2. `App.vue` inflight 去重加时效兜底：entry 存 `{seq, at}`，`Date.now()-at > 35s` 视为僵尸
   直接放行新请求（fetch 已有超时后，这层是保险丝）。

### 验证
- 单测/手测：devtools 里把某个接口挂起（断点或 throttling），确认 30s 后自动报错、后续
  事件驱动刷新恢复；`npm run build` 绿。

## 三、【P0·前端】SSE 活性检测 + 兜底轮询 + 发送回读（根因 C，P1-1/3/4、P2-5）

### 根因
- `App.vue:362-421` `openSSE`：无 `open` 监听（重连成功不补偿）、无活性看门狗。SSE 半开
  挂死时（Vite 代理重启/后端重启窗口）浏览器不报 error、不重连，`lastNetRefresh` 路径
  （`error` 原生事件 15s 节流刷新）也不触发——**所有事件驱动面板静默冻结**。
  实证：`12:17:21` 后端写入并广播了「⏹ 已取消」(PG #78) + `cancelled`/`agent_msg` SSE，
  前端两者皆未收到（t33–t35 stage chips 原样、聊天流停在 12:06）。
- `App.vue:428-436` producing 期间 5s 定时器**只拉 activity**，从不重查 `GET /project`：
  `producing` 是后端内存标志（`agent.go:135` IsRunning），取消要等 runner 收尾（宽限 60s，
  `produce.go:350`）。`@cancel` 处理器（App.vue:665）`await api.cancel(); refresh()` 只刷
  一次，大概率撞上收尾期 producing 仍 true → UI 永远「制作管线运行中」（截图实锤）。
- `ChatPanel.vue:23-37` `send()` 成功后**自己从不回读消息**：自己那条消息要等 SSE `msg`
  事件才上屏。SSE 一死，用户看到「输入框清空、消息没发出去」→ 重复发送（P1-1 的前端半）。
- 过程页只在 `view.producing` 时轮询；prep 链 15 分钟 `producing=false` 且 ② 风格站内部
  无 SSE 事件（`prep/style.go:90/1512` 只有 running/done 两帧）→ 过程页冻在 ① 的最后一行
  （t05 实锤：停在 10:41:03）。

### 修复（`web/src/App.vue` + `server/internal/api/server.go` SSE 端点）
1. **活性看门狗**：
   - 服务端 `server.go:2080` 心跳注释帧 `: ping` 改为具名事件 `event: ping`（前端可见）；
   - 前端 `openSSE` 监听 `ping` 更新 `lastBeatAt`；每 20s 检查一次，`OPEN` 状态且
     `>45s` 无心跳 → `es.close(); openSSE(id)`（心跳 15s，45s = 3 个周期全丢）。
2. **重连补偿**：`es.addEventListener('open', () => refresh())`——每次（重）连成功做一次
  全量对账（服务端 replay 窗 64 条 + 这里一道主动拉取，双保险）。
3. **busy 轮询统一**：`App.vue:428` 的 watch 条件从 `view.producing` 扩为
   `view.producing || prep.running || turnActive`，interval 内：
   - 每 5s：`loadActivity` + `loadMsgs`（很轻，增量接口）；
   - 每 10s（隔一跳）：`loadProject`——`producing` 是内存态，只有重查 `GET /project`
     才能让「取消/崩溃/他机接管」落地为 UI 事实。这直接修掉 P1-3：取消后最多 10s
     视频页离开「制作管线运行中」。
4. **取消收尾轮询**：`@cancel` 处理器改为发出 `api.cancel` 后以 3s 间隔重查 `loadProject`
   直到 `producing===false`（上限 70s ≈ cancelGrace 60s + 余量），随后 `refresh()` 收尾。
5. **发送回读**：`ChatPanel.send()` 在 `api.chat` 成功后不依赖 SSE——App 侧把
   `@sent="markBusy"` 换成 `@sent="onChatSent"`（`markBusy(); loadMsgs()`）。
   （不加乐观 append：202 后立刻回读，实现更简单且不引入去重逻辑。）
6. **取消终态文案**：`format.ts:17` `lastProduceFailed` 不含 `.cancelled`；修 producing
   传播后，取消态会落到 VideoPane `readyToStart`（「终审已通过，随时开工」）。可用但语义
   错位——补一个 `lastProduceCancelled` 分支，显示「已停止制作——产物已保留，对话栏说
   『继续』可重跑」。同时把「已取消」的聊天确认（后端 #78 那条）靠第 3/5 条自然带出来。

### 验证
- 手测脚本：制作中 `taskkill` 后端 → 前端 45s 内自动重连并恢复一致（producing=false、
  聊天出现中断条）；制作中点「停止」→ ≤70s 内视频页离开运行态 + 聊天出现「⏹ 已取消」；
  聊天发送后拔 SSE（devtools block events 接口）→ 自己的消息 1s 内上屏。

## 四、【P1·后端】chat 落库吞错 + 终审确认无持久错误面

### 4.1 消息静默丢失（P1-1 后端半）
`server/internal/api/server.go:1600`：
```go
_ = s.Store.SaveMsg(m)   // 错误被丢弃
```
PG 短暂不可达（SSH 隧道抖动）时：用户消息没落库，接口照样 202，前端清空草稿、无任何
错误——这正是 PG 里 11:04:57→11:21:30 零用户消息、而测试者报告「输入框被清空但消息
没发出去」的成因（前端清草稿的先决条件是请求 resolve，而 resolve 的先决条件本应是
落库成功）。

**修复**：
```go
if err := s.Store.SaveMsg(m); err != nil {
    c.JSON(500, gin.H{"error": "消息保存失败（存储暂不可用），请稍后重发"})
    return   // 不起 Agent 轮；前端 catch 保草稿 + toast
}
```
（429 队列满那条路径在 SaveMsg 之后，语义不变：落库成功但未排队执行，历史可查。）

**验证**：单测模拟 Store 报错 → 500 + 无 Emit；`messages_test.go` 补用例。
另把该窗口的服务端日志翻一遍确认是否 PG 抖动（`ListMsgs 失败` 有 log.Printf 留痕，
server.go:1695），属事后归因，不阻塞修复。

### 4.2 终审两段式确认（P1-2）
`web/src/components/PrepPane.vue:30-49` 的两段式逻辑本身是对的（t15 截图可见 armed 态
生效）。实测「6 连点全失败、按钮弹回、无提示」的实际链路：第二次点击确实发出了
`POST /prep/confirm`，但撞上后端被外部重启的窗口——请求失败（或经根因 B 挂死很久），
错误只走 `message.error` toast（~3s 自灭），按钮已 disarm，截图 t16–t18 与 toast 擦肩。
11:28 同一端点从 StylePane 调用即成功（manifest `prep.confirmed` 11:28:20），证明端点与
校验无恙。

**修复**（前端，PrepPane）：
1. 确认失败不再只靠 toast：header 下加一行持久错误条（下次点击或成功时清除），显示
   服务端 error 原文——测试者当时就能看到「服务暂不可达/AI 还在准备工位上工作」。
2. 失败保留 armed（3s 窗内可直击重试），降低「击穿待确认态」的挫败感；arm 窗口 3s→5s。
3. 请求超时随根因 B 的 30s 生效，`confirming` 不再无限悬挂。
   （根因 B 修复后，「点了没反应」的另一半场景——fetch 挂死期间 confirming=true 吞掉
   后续点击——也随之消失。）

## 五、prep 链过程可见性（P2-5/6/7/8，根因 D）

### 根因
异步准备链（想法页 `runPrep`）推进期间：
- 各站只发 `stage` 事件（`prep/script|style|storyboard`），而 App 的 stage 监听
  （App.vue:374-387）只更新 stageState + loadMsgs + activity，**不触发 loadProject**；
- `prep_updated` 事件目前只有对话内重跑路径在发（`agent/tools.go:98`），异步链全程不发；
- 于是 `view.gates`、`manuscript`、`style`、`prep.exists/running` 全部冻结在链启动前：
  文稿页 0 字（t04，实际 831 字已落盘）、风格页停在「①选风格」初始态（t07）、三工件
  齐了想法页还写「准备阶段进行中」（t08 前）、05 终审页签迟迟不插出。

### 修复
1. **后端发事件**（一行级）：`prep/run.go` 链驱动处，每站 submit 落盘后
   `d.emit(p.ID, "prep_updated", "", station)`；链终态（done/error/cancelled）同样发。
   前端已有监听（App.vue:399 → loadProject），零前端改动即全线解冻。
2. **stage 监听顺手补**：App.vue stage 监听里对 `prep/*` 前缀的 done 事件追加
   `throttledLoadProject()`（与 tool_result 同款 3s 节流）——即使后端事件漏发，站完成也
   会刷新工件面。
3. **风格页 prep 态**（`StylePane.vue`）：拿到 `prep.running`（或 prep 存在且
   style_draft 门未过）时，顶栏显示「风格工位生成中——进度见『主题/想法』页」的占位态，
   隐藏选风格入口与跨项目推荐卡（t07 的「凌晨站台」误导即除）。样张逐张落地后可经
   `artifactFileURL(id,'style/sample-N.png')` 直出缩略图（文件已在白名单内），属增强项。
4. **过程页 prep 轮询**：根因 C 第 3 条的 busy 轮询已把 `prep.running` 纳入——② 风格站
   15 分钟里过程页每 5s 跟 manifest（`prep.step` 行一直在写），冻结即除。可选增强：
   style.go 样张循环每轮 emit 一条 `progress`。

### 验证
- 3 分钟测试片新建重跑：① 完成时文稿页立即出字数；② 进行中过程页时间戳推进；
  三工件齐的瞬间想法页标题离开「进行中」、05 终审页签插入。
