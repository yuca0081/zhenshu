# AI-doom 歌词 MV · 案例解析与立项评估

> 状态：v1（2026-09-28）。样本：B 站 DASH 流（HEVC 1080p30 / AAC 48kHz，156.7s，
> 本地样本 `42246409074-1-30077.m4s` + `-30232.m4s`，ffmpeg 合成为 `tmp_agi_ref/agi_ref.mp4`）。
> 结论来源：低清全片通看 + 每 8s 抽帧 20 张逐帧核对 + 双流探测。
> 定位：表现力层 v2 落地后的第二块试金石——`docs/analyes/group-theory-video-analysis.md`
> 里的 P0/P1 大多已兑现（scene 通道 / formula / 双语字幕 / 转场 / 后期链路，见 `docs/plan.md` §11），
> 本篇回答"这类片子还差什么"。上位文档 `docs/plan.md`；姊妹篇 `docs/analyes/ink-fluid-analysis.md`。

## 1. TL;DR

**这不是"词汇表瓶颈"了，是"主时钟 + 音频供给 + 资产密度"三件事。** 样本是一首
AI-doom 主题歌曲的歌词 MV（kinetic typography）：全片无旁白，歌曲节拍是唯一时钟，
歌词逐词打在画面上。它的主干视觉语言——暗底网格 + 橙红霓虹 + 终端打字机 + 数据图表 +
大字排版 + 颗粒色差后期——恰是 v2 之后咱们已有的能力面（「暗空霓虹」风格同源）。

真正缺的按序：

1. **主时钟（最大缺口，架构预留未实现）**：`timing_basis` 枚举了 `music`
   （`types.go:31`、校验 `types.go:83`），但全仓库没有任何一处消费 music 分支——
   无歌词输入契约、无节拍/onset 检测（全仓库搜 beat/onset/节拍，仅命中的是曲目名
   "upbeat"（`make_bgm.py:189`）和 SSE 心跳（`server.go:784`））、storyboard 时长
   与入场时刻全部挂在 TTS 时间戳上。
2. **MV 组件包（有通道、没货）**：打字机终端、歌词墙、翻牌计数器、印章表单等
   每个都是一份 scene 参考实现的"补货"活，不是"修路"活。
3. **音频供给**：歌词 MV 的主音轨是一首带人声的歌，咱们供给侧只有 TTS + 9 首
   纯器乐程序化 BGM（`data/library/media/audio/tracks.json`）。做这个品类必须
   引入外部歌曲（用户供曲+供词），这同时是新输入契约与版权问题（需拍板）。
4. **3D 实体渲染资产**：Shoggoth 雕塑、纸clip 海、黑洞、发光笔记本是 Blender/AE
   级 DCC 资产，HTML 管线做不出实体渲染质感，只能外部素材引入或降级。

结论：**值得立项，定位是"音乐驱动模式"（timing_basis=music 落地）+ MV 组件包，
不是表现力层 v3。** 全自动复刻到原片的镜头密度不可达（重度手调 motion design），
"风格神似、结构同构"的自动产出可达；约 34/40 镜头的主干在现有通道内，约 6 个
镜头点睛在 DCC 资产上。

**全片统一的设计系统**（高级感来源）：黑底网格/坐标纸 + 橙红·白双色 +
grotesk 巨字与等宽终端字混排 + 全片颗粒/色差/扫描线滤镜 + 歌词与音乐节拍逐词对拍 +
反复回环的母题（笑脸 HUD、终端提示符、P(doom) 计数、Regenerate 按钮）。

**音频**：AAC 48kHz 立体声，全程歌曲（人声+编曲），歌词即文案，商业级响度。

## 3. 咱们现状对照（路径:行号）

### 3.1 已经不是瓶颈的（v2 兑现项）

- **scene 通道**：`kind=scene` 全画幅确定性画布，code 预算 8000 字
  （`render_spec.py:1008`，与 `spec.go:131,382,404` 等契约同值）——粒子、曲线、
  等高线、文字墙、线框 3D 投影都有路走。
- **后期链路**：整片统一暗角+颗粒+色差（风格 token 配强度）——原片的胶片感滤镜这条已齐。
- **全局 HUD / 双语字幕 / 转场黑场微叠化 + 转场 sfx 层**（whoosh/riser，
  `make_sfx.py`、`pipeline.go` 侧链混音）/ camera 关键帧 / `kind=formula`。
- **风格**：15 风格注册表含「暗空霓虹」（深空黑+辉光）——与样本设计语言同源，
  色板换橙红即可。
- **词级时间戳机制**：`tts_align` 逐词高亮的消费端机制已有，只是时钟源是 TTS。

### 3.2 缺口一：主时钟（music 模式只有枚举值）

- `types.go:31` 枚举 `narration | music`，`types.go:83` 校验放行，之后**无一处分支消费**：
  storyboard 生成、段时长、元素入场时刻全部由 TTS 时间戳驱动。
- 无歌词输入契约：project/storyboard 层没有 `lyrics` 字段，没有 LRC 解析，
  没有音频文件上传通道（素材库 catalog 目前只收图）。
- 无节拍/结构分析：没有 onset/beat/tempo 检测代码（grep 证据见 §1），
  也没有"分析产物落盘→渲染期只读"的先例约束。

### 3.3 缺口二：MV 组件包（通道在、库里没货）

方法库 scene 参考实现与注入清单里没有 MV 类模板。需要的"补货"清单：
打字机终端（光标+sampler 面板）、歌词墙（逐词/逐行对拍入场）、翻牌计数器、
纸面表单+橡皮章、[MASK] 词条、状态形变笑脸 HUD、UI 按钮收尾卡、文字墙铺排。
每个 50–200 行 scene 代码，属可枚举的确定工作量。

### 3.4 缺口三：音频供给侧

- BGM 曲库 9 首纯器乐（`data/library/media/audio/tracks.json`，`make_bgm.py`
  程序化合成），无人声能力，TTS 是念白不是唱。
- 歌词 MV 的主音轨必须是真歌 → 新输入契约（用户传曲+词）、音频时长/解码探测、
  版权来源声明，三者都是新的，且版权需要拍板（同 `docs/plan.md` M2 时的 BGM 版权顾虑）。

### 3.5 缺口四：3D 实体渲染资产

Shoggoth、纸clip 海、黑洞、鳞片浮雕、发光笔记本为 DCC 资产（Blender/AE 预渲染），
HTML 管线表达不了实体材质与光影。可选路径：(a) 外部素材引入——但 catalog 目前
只收图，**视频片段资产通道不存在**（水墨篇"离线渲染 mp4 入库"先例可迁移）；
(b) scene 手写线框/粒子近似（气质打折）；(c) 该类镜头明确降级跳过。不可全自动生成。

## 4. 归因

1. **主时钟**（主因）：music 枚举无实现，而这类片 100% 的节奏结构挂在节拍上。
2. **音频供给**：没有歌，品类不成立；这决定了 P0 必须先做"自持曲库卡点片"而非歌曲 MV。
3. **组件补货**：通道在、模板没货，LLM 裸写对拍数学不可靠，必须组件化。
4. **3D 资产**：管线外能力，只能素材引入或降级，不是本仓代码能解决的。
5. **不是瓶颈的**：渲染器/分辨率帧率/后期质感/大字排版/数据图表/公式——v2 后全部同代；
   `tmp_agi_ref/agi_ref.mp4` 与咱们的 1080p30 渲染规格一致。

## 5. 立项方案（建议排期：表现力层 v2 收尾后，暂名 M-D「音乐驱动模式」）

### P0：timing_basis=music 落地（主时钟，先做卡点不碰歌曲）

1. **输入契约**：project 增 `{ music_track, offset }`（自持曲库曲目）；
   storyboard 头 `timing_basis: "music"` 走既有校验。
2. **节拍/结构分析**：Python 侧新增分析脚本（librosa onset/beat/tempo，或 ffmpeg
   ebur128 响度分段），产出 `beatmap.json`（BPM、小节/乐句边界、onset 列表、能量包络），
   **落盘一次入库绑定，渲染期只读**——同输入同输出的确定性约束。
3. **storyboard 适配**：music 模式下段落边界对齐乐句/小节；元素入场允许挂
   `at_beat` 索引，渲染前 bake 成秒（契约层新增一个可选字段 + bake 步骤）。
4. **回归隔离**：music 分支仅影响 storyboard 与 bake，渲染/拼接/后期链路零改动；
   旁白模式全量回归（constants_drift_test 同款门禁思路）。
5. **验收**：用自持 BGM 曲库任一首出 60s 卡点宣传片——不依赖外部歌曲即可闭环。

### P1：MV 组件包（方法库补货）

6. §3.3 清单八件组件，每件一份 scene 参考实现 + 注入清单条目；`at_beat` 驱动入场；
   prompt 侧增"MV/卡点"构图公式（同方法库注入主线）。
7. 打字机终端与歌词墙优先（样本中出现频次最高，亦是普适组件）。

### P2：歌曲品类与视频素材（均需拍板）

8. **外部歌曲开放**：用户供曲+供词（版权声明 UI）、LRC 对齐（无 LRC 走离线强制
   对齐或人工微调，后置）。版权边界未拍板前不做。
9. **视频片段资产通道**：catalog 收视频素材，stitch 叠底合成（水墨篇路线迁移），
   Shoggoth 类点睛镜头走外部素材。

### 明确不做

- 不上 Blender/DCC 渲染管线；不做自动生成歌曲/人声；
- 不追求 1:1 复刻原片镜头（手调密度不可达，目标"风格神似、结构同构"）；
- 不在渲染期重算节拍分析（确定性红线）。

## 6. 风险与待定

- **节拍分析跨版本漂移**：librosa 同输入确定、跨版本可能漂移——beatmap.json 落盘
  即冻结，工具链版本与分析结果一起入库。
- **LLM 用对拍组件的可靠性**：组件模板化让 LLM 只填词/选节拍点，不裸写 beat 数学；
  写砸降级为静态帧（scene 既有兜底）。
- **版权**：P0/P1 只用自持曲库；用户歌曲与 P2 绑定拍板。
- **品类漂移风险**：卡点/ MV 是宣传品类的子形态，别让它反噬"科普/解说"主线的
  旁白驱动默认值——music 模式按 timing_basis 显式声明才启用。

## 7. 验收路径

1. **原型闸**：30s 卡点片——beatmap.json 生成 + 元素 at_beat 入场 + 打字机终端 +
   歌词墙，节拍点误差 ≤1 帧（与 ffmpeg 提取的 onset 对照）。
2. **链路闸**：120s 宣传片 music 模式走完 文稿→分镜→样张→成片，旁白模式并行回归无回退。
3. **风格闸**：八件 MV 组件全部入方法库并有注入清单条目，LLM 一次通过率抽查。
4. **（P2 拍板后）**：用户供曲+LRC 端到端一条歌词 MV。
