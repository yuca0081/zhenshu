# zhenshu 成本与生成时长诊断

> 日期：2026-10-20  
> 范围：2026-10-17 ~ 2026-10-19 的项目账本、运行日志、当前代码  
> 目的：解释“token 多、生成慢”落在哪里，并给出可执行的产品/技术优化方向  
> 说明：本文不是“HTML 视频不如 Python 视频”的结论。问题在**场景生产方式**，不在 HTML 这个渲染介质。

---

## 1. 结论摘要

一句话：

> **当前平台的主要成本不是“模型在创作”，而是“模型在反复重读旧上下文、反复重写整段文件、反复被审核打回”。**

三个最重要的判断：

1. **token 大头是输入，不是输出。**  
   最近两个完整项目里，prompt 占总 token 的 **79%–84%**。模型不是写了 5M token，而是被反复要求重读 4M+ token 的旧上下文。

2. **审核是最大成本中心。**  
   段审 + 边界审占总 token 的 **69%–76%**。单次段审可达 14.4 万 prompt，单次边界审可达 14.3 万 prompt。

3. **渲染不是瓶颈。**  
   4m18 / 7746 帧渲染 11m47 ≈ **11 fps**；60s / 1800 帧 Cairo 渲染 2m48 ≈ **10.7 fps**。按帧算两套渲染器几乎一样快。差距在渲染之前的 2 个多小时 LLM 流程。

因此，优化方向不是换语言、换渲染器，而是：

> **把“LLM 写完整 HTML + 多轮多模态审判 + 全文件重写”改成“LLM 写场景 spec / patch + 组件编译器 + 确定性检查 + 单次判卷”。**

## 3. 根因分析

### 3.1 根因一：ReAct 审核上下文“滚雪球”

相关代码：[review.go](../../server/internal/review/review.go)、[agent.go](../../server/internal/review/agent.go)

`Loop.Run` 每一轮都会把：

- 完整 system prompt
- 完整 kickoff（分镜、旁白、设计规则、词级信息）
- 之前所有 tool call / tool observation
- 之前取回的图片
- 新一轮图片

重新发给模型。

审核预算：

- 段审 6 轮
- 边界审 6 轮
- 终审 4 轮

即便加了 `AUDIT_IMG_KEEP_ROUNDS=2` 裁掉旧图，**文本历史、工具历史、最新图片仍然每轮重发**。这就是 prompt 占 80% 的直接原因。

更隐蔽的乘法器是 `get_clip`：

- 一次最多返回 8 帧
- 取证预算 8 次
- 最坏情况下，一次审核可以塞进几十张图
- 代码注释里已经写了“后期单请求顶到 30–40 张图，这是一次审核 5–10 分钟的主因”

**结论：审核成本不是线性的，是“轮数 × 每轮增长的上下文”。**

### 3.2 根因二：修复是“全文件重写”，不是 patch

相关代码：[scenegen.go](../../server/internal/produce/scenegen.go)

`sceneUserPrompt` 包含：

- 契约全文
- 设计系统
- 方法库
- 金样例 HTML
- 词序表
- 上一版 HTML（最长 48KB）
- lint/审核意见

模型被要求返回完整 `html`，而不是只返回改动。

一次修复：

- prompt 约 1.2–1.7 万 token
- completion 约 0.3–0.5 万 token
- 输出 7–10KB 的完整文件

`seg07` 改 10 次，就是 16 万 prompt + 4 万 completion 的量级。

更严重的是质量问题：

- 模型每次重抄整个 JS 文件
- 很容易改变量顺序、作用域、时间线注册
- 日志里 `seg07 check 三轮未过: Cannot access 'Ph' before initialization` 就是这一类

**你在 `redrawFeedback` 里已经写了“只动点名元素，其余逐字保留”，但协议仍然要求完整 HTML。这条指令省不了 token，也挡不住新 bug。**

### 3.3 根因三：任意 HTML/CSS/JS 的运行时错误，只能靠“再生成一次”解决

静态 lint 能挡已知模式，但挡不住：

- `Cannot access 'Ph' before initialization`
- GSAP 时间线注册顺序错误
- 某个元素在特定时刻不存在
- 字体/布局在运行时才炸
- canvas 绘制函数与 timeline 脱节

这些错误在浏览器里才暴露。当前处理方式是：

```text
check 失败 → 重新生成整段 → 再 check
```

每一次都是几万 token 和几分钟。

这不是模型不够聪明，而是**让模型直接写任意 JS，把编译期能发现的问题推到了运行时 + 重写**。

### 3.4 根因四：取消/重试/重启没有细粒度断点

最新项目日志中多次出现整批 `context canceled`：

- 23:16:34：seg02/seg03/seg07/seg09 同时取消
- 23:20:39：seg02/seg07、b05 取消
- 23:24:49：seg06、b03、b04、b05 取消
- 23:33:28：seg04/seg05/seg06/seg08 取消
- 23:35:11：seg04/seg05/seg06/seg08 取消

同时还有：

- `HTTP 400: messages[1].content[4].image_url格式错误` 反复出现
- `HTTP 429` 限流
- `HTTP 500` 网络错误
- 10-19 项目在 13:25 撞到“5 小时使用上限”

一次取消/重启会把这批在飞的生成全部丢掉；下一次只能重跑。日志里同一段被启动 10 次，很大一部分不是审核打回，而是**失败重来**。

另外，`server.log` 明确记录：

```text
[store] PG_DSN 未配置，用内存存储（重启丢聊天记录）
```

生产环境没有持久化 job 状态时，重启会放大重复劳动。

### 3.5 根因五：审核层太多，误报会触发返工

当前至少有：

- `scene_lint`
- `check`
- `frameQA`
- `prereview`
- 段审（6 轮 ReAct）
- 边界审（6 轮 ReAct）
- 全片终审（4 轮）

这些检查有大量重叠。

更关键的是审核误报：

- 《拉普拉斯妖》的手工复盘里，13 个 FAIL 有 7 个是“采样落在动画中途”的假象
- 假阳性 → 打回 → 重写 → 重渲染 → 再审核
- 一次假阳性可能烧掉几万 token 和十几分钟

审核模型没有“证据不足就放过”的机制，也没有“这条 high 值不值得修”的预算判断。

### 3.6 根因六：每片重新发明设计系统 + 全局 LLM 并发只有 2

相关代码：[provider.go](../../server/internal/llm/provider.go)

- `llmGate` 默认 **2 路并发**
- 上层写 4 / 审 4 只是排队，真正同时在跑的 LLM 只有 2 个
- `Chat` 默认超时 600 秒

每个项目还要先跑：

- 文稿
- 风格系统 + 样张（10-18 为 17.1 万 token，10-19 为 26.6 万 token）
- 分镜（5–7 万 token）

设计系统还是“每片现发明”，没有复用。这部分是固定成本，不是某段代码写得慢。

## 4. 现有资产与正确判断

这套平台不是从零开始，已经有不少正确的东西：

### 应该保留的资产

- **TTS + 词级时间戳**：把字幕/动画锚点精确到词，是平台相对“手写代码”的核心优势
- **段级流水线 + 分段缓存**：方向正确，问题在场景生产层
- **HyperFrames check / 渲染 / 拼接**：渲染速度不慢，不需要换 Cairo
- **风格库 / 方法库 / 金样例**：可以继续复用，但要从“提示词注入”升级为“组件参数”
- **agentlog / manifest**：现在能算清 token，这是做优化的前提
- **代码注释中的事故日期与原因**：非常珍贵，不要丢
- **降级放行 / fallback**：工程上务实，保留

### 不应该得出的结论

- ❌ “HTML 视频不如 Python 视频”  
  → HTML 作为通用视觉栈上限更高；问题在“每段自由写 HTML/JS”。
- ❌ “平台没必要做了”  
  → 单部高定片可以赢过平台，但平台的价值在批量、编辑、协作、一致性、非专业用户。
- ❌ “换 Python 就能解决”  
  → 如果让模型每段写 Python，同样会有运行时错误、重写和审核成本，还多出沙箱/依赖问题。
- ❌ “加更多审核 agent 就能提升质量”  
  → 审核已经占 69–76%，再加只会更贵、更慢、更容易误报。

## 5. 目标架构

### 5.1 从“模型写 HTML”到“模型写 spec + 编译器”

现在：

```text
LLM → 完整 HTML/CSS/JS → 渲染 → 截图 → 多模态审 → 再写完整 HTML
```

目标：

```text
文章/数据
  → 文稿/分镜（LLM）
  → SceneSpec（LLM 选组件 + 填参数 + 写文案）
  → 编译器（平台预测试组件：HTML/CSS/Canvas/WebGL）
  → 确定性检查（lint/check/对比度/溢出/首末帧）
  → 单次联系表判卷（1 张图，4–6 帧）
  → Patch（元素级修改）
  → 只重渲染改动段
```

模型只做四件事：

1. 选叙事结构
2. 选镜头/组件
3. 写文案
4. 填参数、发 patch

不再写任意 JS。

### 5.2 组件库的初始范围

先做 15–20 个引擎，覆盖 80% 的知识/数据解说镜头：

- 标题/字卡
- 要点列表
- 引用/金句
- 数据图表
- 对比/前后
- 时间线
- 流程图
- 地图
- 人物/产品卡片
- 屏幕录制/UI 演示
- 粒子/星空
- 轨道/天体
- 波形/概率云
- 3D 物体/旋转
- 相机推拉/转场

每个引擎需要：

- JSON schema
- 参数范围
- 预览
- 单元测试
- 性能预算
- fallback

### 5.3 把《拉普拉斯妖》拆成引擎

这不是丢掉那支片子，而是把它变成资产：

1. `starfield`
2. `orrery`
3. `eye`
4. `worldlines`
5. `probability-cloud`
6. `lorenz`

下一部片子的 60–80% 可以由这些引擎组合出来。  
**这才是把“高定”变成“产品”的路径。**

## 6. 优化路线图

### P0：止血（1 周内）

目标：不再为同一个失败重复付费。

1. **每个项目/任务加 token 预算与调用上限**
   - 超过预算就停，不允许“再修一轮”无限烧
   - 用现有 `agentlog` 做实时账本

2. **每个 LLM 调用成功即落盘**
   - scene、audit、verdict 都要幂等键
   - 取消/重启后从最后一次成功调用恢复，而不是整批重跑

3. **修 `image_url` 400**
   - 发请求前校验 `data:image/...;base64,` 前缀、长度、空图
   - 记录 URL 来源与哈希，别再反复拉起审核

4. **同错误签名重试两次就 fallback**
   - `check` 同一错误连续两次，直接沿用上一版/模板，不再全量重生成

5. **任务去重**
   - `(project, task, input_hash)` 相同且在飞的任务不重复启动

**验收**：同一段重复启动次数 < 1.2 次/段；取消不再丢整批。

### P1：patch + 单次判卷（2–4 周）

目标：把最大成本中心砍一半。

1. **修复协议从 full HTML 改为 patch**

```json
{"patches":[
  {"target":"#s3-title","set":{"text":"...","style":{...}}},
  {"target":"#s3-orbit","set":{"timing":{"start":4.2,"end":7.8}}}
]}
```

- 输出从 3–5k token 降到几百 token
- 不重抄全文，不引入新 bug
- 只 lint / 预览改动部分

2. **审核从 ReAct 改为单次联系表判卷**
   - 每段 4–6 张落定帧，拼成一张 2×2 联系表
   - 图上烧录 `t=...` 和“此刻应该出现什么”
   - 一次请求，一个结构化意见单
   - 只有动画接续/转场才允许一次 `get_clip`

3. **先跑确定性检查**
   - 对比度、溢出、运行时报错、首末帧差、字幕安全区
   - 机械问题不进多模态审核

4. **稳定前缀 + 缓存**
   - system + 契约 + 风格 bible + 金样例放最前
   - 场景变量放最后
   - 如果端点支持，显式开 prefix cache
   - 审核结果按场景内容哈希缓存

**验收**：审核 token 下降 ≥ 50%；写画面 completion 下降 ≥ 50%；首次通过率不明显下降。

### P2：SceneSpec + 编译器（4–8 周）

目标：让 60% 的镜头不再需要模型写代码。

1. 定义 `SceneSpec` schema
2. 先做 8–10 个高频组件：标题、要点、引用、图表、时间线、对比、粒子、轨道
3. LLM 只输出 spec
4. 组件编译为 HTML/Canvas/WebGL
5. 自定义 HTML/JS 只作为 escape hatch，按“新组件”流程测试、缓存、复用

**验收**：组件覆盖率 ≥ 60%；运行时错误率 < 2%；3 分钟片 token < 1.5M。

### P3：产品化（2–3 个月）

1. 20–30 个组件
2. 品牌包 / 风格包复用，不再每片重新发明设计系统
3. 多版本：16:9 / 9:16 / 中英双语
4. 批量生成 / 数据绑定 / 本地化
5. 可编辑时间线 / 元素级修改 / 版本对比 / 审核流
6. 组件市场或插件 SDK

**验收**：3 分钟片 < 1M token、< 45 分钟墙钟、首次通过率 > 70%、品牌一致性可量化。

## 7. 指标：以后只看这几个数

不要只看“生成时长”，建立统一账本：

| 指标 | 定义 | 目标（建议） |
|---|---|---|
| `tokens_per_minute` | 总 token / 成片分钟 | 先降到 250k/min 以下 |
| `prompt_ratio` | prompt / 总 token | < 70% |
| `calls_per_minute` | LLM 调用数 / 成片分钟 | 持续下降 |
| `first_pass_acceptance` | 首次审核通过段数 / 总段数 | > 70% |
| `rewrite_rate` | 重写段数 / 总段数 | < 1.5 次/段 |
| `component_coverage` | 组件生成镜头 / 总镜头 | > 70% |
| `runtime_error_rate` | check 运行时错误 / 段数 | < 2% |
| `cost_per_video` | 单条成片成本 | 按业务定价倒推 |

建议按“每分钟成片”而不是“每个项目”做预算，因为项目长度差异很大。

## 8. 不建议做的事

- **不要整体换 Python**  
  现有 TTS、词级时间戳、分段渲染、审核、HyperFrames 都是资产；换语言会丢掉浏览器预览/指哪改哪的根。

- **不要继续加审核层**  
  审核已经占 69–76%；再加只会更贵、更慢、误报更多。

- **不要追求“任何视频”**  
  通用生成会被模型公司吃掉；收窄到知识/数据/报告类解说，才有平台价值。

- **不要在减少调用次数前加并发**  
  只会更快撞 429 / 5 小时上限。

- **不要让模型每段从零写任意 JS**  
  这是当前成本和运行时 bug 的根源。

- **不要每片重新发明设计系统**  
  风格库应该复用、参数化，只在用户明确要新风格时重新生成。

## 9. 产品方向建议

技术优化必须配一个收窄的产品定位，否则会变成“更便宜但不知道服务谁”。

建议定位：

> **把一篇中文长文/报告，在 30 分钟内变成一条品牌一致、可修改、可审核的知识解说视频。**

目标用户：

- 企业市场部 / 研究机构
- 媒体 / 知识付费 / 课程团队
- 需要批量、多语言、多版本的 B 端客户

核心卖点：

- 文章 → 成片的全链路
- 中文 TTS + 词级字幕 + 时间线
- 品牌一致性
- 可编辑、可审核、可回退
- 多格式 / 多语言 / 批量
- 数据/图表/引用可追溯

不要拿《拉普拉斯妖》当产品基准。它是品牌片/高定片，适合 showcase，不适合日常产能。

## 附录 C：数据复现

聚合脚本（在仓库根目录运行）：

```python
import json, glob, os, collections

for d in sorted(glob.glob("data/projects/*")):
    m = os.path.join(d, "manifest.jsonl")
    if not os.path.exists(m):
        continue
    p = c = cached = calls = 0
    by = collections.defaultdict(lambda: [0, 0])
    for line in open(m, encoding="utf-8", errors="replace"):
        try:
            e = json.loads(line)
        except Exception:
            continue
        if e.get("type") != "agent.done":
            continue
        pt = e.get("prompt_tokens", 0)
        ct = e.get("completion_tokens", 0)
        p += pt
        c += ct
        cached += e.get("cached_tokens", 0)
        calls += e.get("calls", 0)
        task = e.get("task", "?")
        key = ".".join(task.split(".")[:2]) if task.startswith("seg.") else task.split(".")[0]
        by[key][0] += pt
        by[key][1] += ct
    print(os.path.basename(d), "total", p + c, "prompt", p, "completion", c, "cached", cached, "calls", calls)
    for k, v in sorted(by.items(), key=lambda x: -(x[1][0] + x[1][1])):
        print("  ", k, v[0], v[1], v[0] + v[1])
```

---

**最终一句话：**

> 你不需要一个更聪明的模型，你需要一个更便宜的迭代闭环。  
> 先让模型少读旧上下文、少写整段文件、少被打回；再把场景变成可组合的组件。  
> 这样平台才能既保留通用性，又接近高定片的质量。
