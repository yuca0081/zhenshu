## 问题清单（按优先级）

### 高

**P1 样张画布写死 960×540 横版，不跟随项目画幅**
- 现象：项目 9:16 竖屏，三张样张实测全部 960×540（16:9 横版）。
- 根因：`server/internal/prep/style.go:323` render_sample 工具描述把画布写死 `width:960px;height:540px`。
- 危害：竖版项目的构图/版式在横版样张上验证=无效验证（字号占比、纵向排布、三柱横排是否溢出全都失真）。这正是风格库老坑「横版版式×竖版画布」的复发路径——样张横版→风格包按横版思维写版式→成片竖版落地走样。本次成片帧侥幸竖版正确，但版式带宽的验证环节是缺失的。
- 建议：render_sample 按 project.aspect 传画布（9:16→1080×1920 或等比缩小），工具描述同步参数化。

**P2 submit_style 参数类型不匹配连败 4 轮（白烧 2 分钟）**
- 现象：风格工位 r6–r9 连续 4 轮提交被拒：`radius` 该 int 给了 string、`weight` 该 string 给了 number、`layered` 该 string 给了 bool，r9 又因「skin 四个必填槽位为空」被拒，r10 才提交成功。
- 根因一半在 schema 反直觉：`fonts.display.weight` 是 string（"bold"而非 700）、`layouts[].layered` 是 string（模型天然给 bool）；另一半在报错是 Go 原生 unmarshal 文案，模型难自查。
- 危害：每轮 ~30 秒 + 吃掉工位回合预算（本预算放宽到 30，这次烧了 4 个在格式上）；换个更保守的模型可能直接卡死在准备阶段。
- 建议：①工具 schema 里给 design_system 的字段类型示例值；②对 weight/layered 这类字段做宽容归一（数字字重→映射字符串、bool→"yes/no"）；③报错改人话（字段路径+期望类型+收到什么）。

### 中

**P3 search_styles 分面 0 命中时报「库内共 0 条」，误导模型**
- 现象：`{"mood":"明快"}` 两次 0 命中且提示「库内共 0 条」，但同会话无分面搜索「命中 6 / 共 6 条」——库里有货，是分面无命中，文案却说全库为空。
- 危害：模型多花一轮换策略（本次侥幸恢复）；若模型信了「库空」可能直接放弃库内检索改自造风格。
- 建议：分面搜索的空结果文案改成「该分面 0 命中（库内共 N 条）」，并提示可放宽哪个分面。

**P4 预审修复后全量重审，seg02 三轮才过，预审占总制作时长 43%**
- 现象：round1 仅 seg02 挂（2 个问题）→修复→round2 **全量 10 段重审**，seg02 反而挂出 4 个问题（越修越多）→再修复→round3 又全量重审才全过。预审总耗时 13 分 17 秒，占整片制作 31 分 39 秒的 43%。
- 危害：每轮全量重审 ~2.5 分钟纯视觉调用；修复不收敛时成本线性放大。
- 建议：修复轮只重审被修复的段（+可选与其舞台连续的相邻段）；全量重审仅在第 2 次修复仍挂时触发。另：修复提示词宜带上「上一轮问题清单」，避免修 A 破 B。

**P5 事件流浮层遮挡下方按钮，点外部不收起**
- 现象：点开「事件流」后浮层（feed-pop）悬浮在主区上方，「确认打包，允许开工」按钮被其空态 div 拦截点击；点击浮层外区域也不收起，必须再点一次「事件流」按钮本身。真人用户点开事件流再想确认打包会踩同一坑。
- 建议：浮层加 outside-click 收起 + Esc；或限制浮层高度不盖主区操作按钮。

**P6 新流程下页签状态文案脱节**
- 「视频」页签在三件齐+终审通过后仍显示旧空态「三件事齐了就开工…先填文稿」；
- 终审摘要行风格显示源库名「跟着 Unsloth 学量化：GGUF 到底是什么？」而非移植后的项目风格名「奶油涂鸦厨房台 · 洋葱反击战」（② 区块标题是对的，摘要行误导）。

### 低 / 观察

- **P7 分镜备注泄漏成画面文案**：seg02 帧内出现「臭味波浪线涂鸦脸」——场景代码把分镜括号注记（涂鸦脸画法说明）当可见文案渲染了。建议分镜注记与可见文案在数据结构上分字段。

- **P14 环境差异**：本机无 PG，风格库账本走文件；PG 版 search_styles 行为可能与本次不完全一致，评审 P3 时注意。
