### 3. LLM 限流（GLM 1302/429）连环杀手 ⭐ 本次最大问题
- 时间线：17:42 首次制作起，几乎每轮制作都死于"场景生成 3 次尝试均失败 HTTP 429"。
- 三层根因层层揭开：
  1. **writeSem 死代码（真 bug）**：`segpipe.go` 的写信号量创建了但 writeSegment 从没
     acquire——15 个段的场景生成完全无并发上限地齐发。已修（3 行接线），测试绿。
  2. **check 修复轮的 sceneGen 重生成不走写信号量**（segCheck 内直调），多段同时修复时
     仍会瞬时并发超限。未修（改它要动审核工位结构，留 TODO）。
  3. **429 退避不够**：provider 3 次尝试（15s/30s 退避）对这种紧限流不够；多调用方
     同步退避同步重试=惊群。未修。
- 环境变量三层并发旋钮里只有 `PRODUCE_AUDIT_CONCURRENCY` 真生效；
  `SCENE_CONCURRENCY` 的信号量是每次调用各建各的，段级路径下形同虚设。
- 干预：写并发 1 + 审计并发 1 重启；死亡后靠 journal 断点续跑（每次重拉只补没过的段）。

### 4. 检查器跨段误报 → 修复轮永不收敛的幽灵违规 ⭐ 第二大问题
- 现象：seg01/04/13/15 的 check 全部报 `#seg02-title` 违规；seg04-15 全部报 `#sg8-cur` 违规——
  而这些元素只存在于 seg02/seg08 自己的文件里（grep 铁证）。
- 根因：段级 check 子工程把整个 `compositions` 目录 junction 进去，hyperframes check
  扫了**所有段**的文件——任何一段的 error 级违规=全体段的 check 失败。
  于是每个段的修复轮都在试图修一个不在自己文件里的错→LLM 修复轮烧穿→重生成的
  10k-token 大调用又喂了 429。两个问题互为放大器。
- 干预：手工修掉 seg02（letterSpacing→删）、seg08（left→删）的违规补间（frames +
  llm/comp-* 双写，防重建覆盖）；seg04 的 glyph 加 CSS transform 对齐真实渲染位置。
  修完当轮 seg08 check 18 秒通过。
- TODO：check 应只扫本段子工程引用的文件，不该扫 junction 全目录。
