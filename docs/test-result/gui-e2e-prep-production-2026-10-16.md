## 二、问题清单

### P1 致命（流程走不通的根因）

**P1-1 终审页「确认打包，允许开工」是死按钮（window.confirm 依赖）**
- 现象：两次真实点击，`POST /api/projects/:id/prep/confirm` 从未出现在服务端日志；第一次点击后整个页面 JS 冻结（evaluate/截图全超时、前端 3 秒轮询停止、进程 CPU 持续高占用），随后浏览器页签丢失只能重开；第二次点击无任何反应（无请求、无 toast、无跳转）。
- 根因（代码定位）：`web/src/components/PrepPane.vue:25` —— 点击处理器第一步是 `window.confirm('确认三工件并锁定设计系统？…')`。原生阻塞弹窗在内嵌浏览器环境（QtWebEngine 系）会被吞掉或挂死页面。普通 Chrome/Edge 桌面浏览器可能可用，但只要在这种嵌入场景用就必挂。
- 后果链：`prep/confirm` 是唯一会把 `style/stylepack.json` 的 `confirmed` 置 true 的入口；而它是制作阶段硬门（`server/internal/produce/segpipe.go:206`）的唯一放行条件。按钮死 → 硬门永远不过 → **标准流程（想法→自动准备→终审→开工）必然卡死**。
- 证据：`shots/t13_final_review_top.png`（按钮在）、服务端日志（23:35–23:46 无任何 POST）、`shots/t15_confirm_pack_2nd.png`（点击后无变化）。

**P1-2 "确认"状态两套定义互相打架，UI 说能开工、一开就报错**
- 现象：风格页确认后，视频页显示"✓ 终审已通过，随时开工……打包终审也确认过了"；点"开始"后 35 秒即报 `风格包缺失或未确认（打包终审硬门）`，自动重跑 2 次、对话"继续"自愈 2 次，**四次全败，每次失败原因一字不差**。
- 根因：风格页「确认风格」走 `style/confirm`，只写 `style_samples.json` 的 confirmed；制作硬门读的是 `stylepack.json` 的 confirmed（要靠 prep/confirm 写）。`/api/projects/:id` 的 gates 和 `/prep` 的 top-level confirmed 都由前者驱动，所以 UI 全是绿灯，制作闸是红灯。
- 附：终审页随后显示"✓已确认，可开工"并**把确认按钮藏掉**（v-else），等于把唯一能救回来的按钮从界面上移除了，死锁彻底封死。
- 证据：`shots/t20_video_tab.png`（随时开工）、`shots/t22_chat_progress.png`（失败+事件流）、activity 接口四条 produce.error。

**P1-3 失败引导指向一条走不通的路**
- 失败文案："请在对话里说明要改什么走准备阶段反馈重跑，**打包确认后再开工**"。但按这个指引：改完→终审按钮因"已确认"不再出现（P1-2）；用对话让风格重跑把状态打回未确认后，按钮重现，但点了还是死（P1-1）。对话智能体工具箱里也没有任何能代替 prep/confirm 的工具（rerun_prep 明确写"完成后等用户在终审页签重新确认"）。即：**照着平台自己的指引操作，永远到不了终点**。

**P1-4 429 限流下恢复路径被堵死（外部因素+平台因素叠加）**
- 风格工位重出时连续 `HTTP 429 账户达到速率限制`（与并行会话/夜跑共用同一 LLM 账户有关），冷重试一次后放弃。测试后半段所有进展被限流吸收。这是已知遗留（见 memory：修复轮收敛难+429限流是遗留），本次实测再次验证：**429 会把交互式测试/多会话并行直接打死**，建议平台侧做账户级并发协调或更长的退避。

### P2 中等

1. **新建视频弹窗创建成功后不自动关闭**：项目已进侧栏、工作区已加载，弹窗还开着且保留上次主题，极易误点"创建"造出重复项目。证据：`shots/t02_idea_filled.png`（背景已是新工作区，弹窗还在）。
2. **首次点击终审按钮把页面整冻结**：JS 主线程被阻塞弹窗挂住 → 轮询停摆 → 页签丢失，用户视角是"平台死了"。见 P1-1。
3. **死按钮无任何反馈**：点击无 toast、无报错、无跳转，用户完全不知道发生了什么、该干什么。
4. **对话栏 Enter 发送静默失效**：00:09 的消息能发出去；00:26 与 00:31 的两条（重发指令、"重试"）fill+Enter 后既不在消息列表、也不报错，最后一张截图可见"重试"还停在输入框里。用户以为发了，对方永远收不到。证据：`shots/t25_final_state.png` 右下角。
5. **文案打架（两处"唯一的人工门"）**：风格页说自己是"唯一必须你拍板的门"；终审页注释说自己是"全流程唯一人工门"；想法页说"每步的详细动作在事件流有账"，但事件流面板叫"制作事件流"，准备阶段全程空白。

### P3 轻微 / 观察

1. 准备全链 19 分钟，界面承诺"一般几分钟"，预期管理失准（其中风格工位含样张生成属正常耗时，但文案该改）。
2. 文稿页签不实时回填：文字稿 23:15 服务端已落（API 可见 507 字），文稿页签一直显示 0 字，直到 23:32 全链结束才出现。中途用户无稿可看。
3. 前端每 3 秒轮询 `audio_meta`，资源未生成期间全是 404（服务日志噪音，建议 404 时降频或改推送）。
4. 首页项目卡片的"上次制作失败"红字很醒目（好），但点进去失败原因要自己翻事件流/对话，建议卡片上带一句人话原因。

## 三、验证合格的部分（值得保留）

- **准备三工位产物质量**：文字稿 507 字/23 句/目标 120 秒（简报"2 分钟"约束生效）；风格包方向、概念、3 张样张、皮肤、字体、动效一应俱全；分镜 15 段带段落链、段表、首末拍。`shots/t13`、`shots/t14_review_scrolled.png`、`shots/t18_style_bottom.png`。
- **质检真实拦截**：样张重出第 6 轮 submit_style 因"skin 四个必填槽位（bg/txt/accent/font）不能为空"被打回——判卷机制在工作。
- **失败信息分层**：对话栏说人话（"碰上了平台限流，不是项目本身的问题"），事件流留技术明细（429 原文、轮次、动作）——符合"对话栏禁技术报错"的既定方针。
- **自动重跑机制**：制作失败自动重跑 2/2 按设计执行；风格工位 429 后有冷重试。
- **服务端状态持久化**：页面冻结、页签丢失、多次重载后项目状态零丢失。

## 四、遗留现场（供复现/修复）

- 项目 `p20261016-231143`：stylepack.json `confirmed=false`；风格重跑失败后 stylepack 已被清空（/prep 的 stylepack=null），终审页显示"准备工位还没跑完（缺工件）"；`style_samples.json` 仍是 confirmed=true（与 stylepack 状态不一致，本身也是 P1-2 的病征）。
- 复现 P1-1 最短路径：新建项目 → 走完自动准备 → 终审页点「确认打包，允许开工」（在嵌入式浏览器里）。
- 修复建议方向（供参考，未动代码）：① PrepPane.vue 去掉 window.confirm，换成站内确认弹层；② 制作硬门与 gates/prep 确认位统一口径；③ `/prep` 已确认时不要隐藏确认按钮的救场路径（或提供"重新打包"入口）；④ 429 冷重试加长退避与账户级排队。
