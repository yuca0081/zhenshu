# vend 阶段方案——平台的"按章办事采购员"(2026-10-01 定稿)

> 背景:风格打样(demo/style-samples,BV1JvaW6JEMb 复刻)验证了「纯代码零素材」风格零障碍、
> 「素材依赖」风格可用素材工位(make_stickers.py)闭环。随之暴露的能力缺口:**场景代码想用
> vendor 目录里没有的框架(如 three.js)时,管线今天的行为是 lint 拦下 → 转人工,通道不存在。**
> 本方案补这个缺口。定稿依据:2026-10-01 会话讨论(无法预测模型需要什么框架 → 不预测,建自动
> 引进通道)。

## 0. 一句话

**模型管"要什么",确定性代码管"怎么来";安装动作 100% 由平台代码执行,智能体只在生产线外
修"方案"。不需要提前预测框架清单,清单随用随长。**

## 1. 两个前置事实(设计的前提)

1. **生产模型的"没手"是刻意设计,不动。** 模型经 API 只产出场景代码,所有执行由 Go 管线的
   写死阶段完成——安全、可审计。本方案不给模型开任何执行权。
2. **"无法预测"是伪问题。** 模型需要 three.js 的那一刻,是在写某段场景代码时——需求出现的
   瞬间需求就明确了。缺的不是预测能力,是一条**自动化引进通道**。契约 A3("新框架走提案→
   确定性审查→进目录")早已预留位置,本方案把"提案→审查"从人工改成机器流水。

## 2. 分工与权限边界

| 角色 | 干什么 | 不干什么 |
|------|--------|----------|
| 模型(设计师) | 场景代码里声明"我需要 three.js" | 不执行命令、不下载、不碰 shell |
| lint(考试官/哨兵) | 机械验收场景文件;**发现"缺库"这一机器事实** | 不猜、不做模糊判定(零误报原则不变) |
| 管线编排(server Go) | 按写死规则触发 vend(与触发渲染同一套逻辑) | 不改规则本身 |
| vend 阶段(采购员,平台代码) | 下载钉版 → 哈希校验 → 验收 → 入库 | 只写 vendor 卷、只访问包源白名单域名 |
| 诊断员(智能体,**生产线外**) | 长尾故障诊断,产出**平台定义补丁**(Dockerfile/manifest/预案) | 不进生产容器、不亲手装 |
| 人 | 定考题、限额、审平台代码与补丁 | 不审每一次具体补货 |

**关键定性:不要"会随机应变的安装工",要"会总结经验的老师傅"。** 生产线上每一步保持确定性
可复现;智能用于把新问题变成旧预案(§6 飞轮)。

## 3. 一个库的旅程(全自动五步)

1. **发现**:lint 发现场景引用 vendor 没有的库(A3 检查项)——机器事实,非模型口头申请;
2. **采购**:管线读 lint 产出的结构化申请单(库名、钉死版本、引用段)→ vend 下载 + 哈希校验;
3. **验收**(核心闸,复用现有资产):
   - 确定性回放:同段渲染两遍,抽帧像素 diff≤契约 T9 容差(sceneReplayCheck 延伸);
   - 禁网:库内无 fetch/XHR/外链(A1 同源检查);
   - 无自带时钟:不触 T2 禁用面(performance.now 等);
   - 体积上限(单库)与开源许可证白名单;
4. **入库**:manifest 登记(库名+版本+哈希+验收记录)→ 重新 lint 放行 → 全平台后续直接领用;
5. **不过关**:违规清单回喂模型换实现路线(修复协议 ≤2 轮,超时转人工)。

## 4. Docker 落地三原则(结合 deploy/Dockerfile 现状)

- **镜像=焊死的常备工具**:gsap、hyperframes@0.8.55(已锁)、fonts-noto-cjk(已装)、
  ffmpeg/chromium(已装)、rembg+u2netp 模型(待加,构建期预下)——断网照常出片,绕开最高频
  失败源;
- **库房=卷,不进镜像层**:vend 补的货落 `data/library/vendor`(compose 已挂 data/library,
  零配置改动),容器重建货不丢——沿用 whisper 模型缓存挂卷的同一条教训(Dockerfile 注释:
  不挂卷则重建重下 1.5GB);
- **考试环境=生产环境**:验收与渲染用同一镜像的 chromium/字体,考过即能用;tech-stack §5
  两容器愿景落地后,渲染面内网隔离,"渲染面禁网"从代码约定升级为物理事实。

## 5. 失败处理(两类分开,铁律不变)

| 类型 | 例子 | 处理 |
|------|------|------|
| 货的问题(模型可改) | 版本不存在、验收不及格 | 违规清单回喂模型重写;黑名单防重复采购 |
| 路的问题(环境故障) | 断网、磁盘满、源不可达 | 暂停+报修+断点恢复,**不**伪装成场景违规 |
| 安全事件 | 哈希不符 | 拒收+报警,不重试 |
| 模型执念 | 反复要同一不合格库 | 黑名单 + 修复协议 2 轮上限(现有保险丝) |

铁律(开发宪法同源):**不静默降级、不无限重试、全程留痕**(台账可见每笔采购:
申请/结果/耗时/验收记录)。渐进开关 `VEND_MODE=off/manual/auto`:上线初期 manual(缺货先
等人确认),跑熟切 auto。

## 6. 智能的用法(经验固化飞轮)

诊断员每解决一个新错误(实例:2026-10-01 rembg 1GB 模型下载超时 → 换 u2netp 4.7MB → 改
脚本重跑),就把解法沉淀为 vend 预案的一条**新分支**("大模型下载失败→降轻量档")。同样的
错第二次出现由预案直接接住。**智能体出场率单调下降,平台预案单调变厚**——能力增长走数据和
清单,不走代码分支(宪法第 2 条)。
